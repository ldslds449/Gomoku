# WebGPU 蒙地卡羅五子棋

在瀏覽器裡和 AI 下五子棋。AI 用蒙地卡羅樹搜尋（MCTS），隨機對局交給 WebGPU compute shader 平行模擬；核心以 Rust 撰寫並編譯成 WASM，在 Web Worker 中執行。沒有 WebGPU 的環境會自動改用 CPU。

## 功能

- **棋盤**：9×9、13×13、15×15。欄位從 A 開始，列號從 1 開始，黑先。
- **規則**：五子以上、恰好五子，或黑棋禁手（長連、雙四、雙三，依正式連珠規則）。禁手模式只用 CPU，其他規則支援 WebGPU。
- **難易度**：

  | 難易度 | 思考時間 | 溫度 T       |
  | ------ | -------- | ------------ |
  | 入門   | 150 ms   | 1            |
  | 簡單   | 500 ms   | 1            |
  | 普通   | 1000 ms  | 0.25（預設） |
  | 困難   | 2000 ms  | 0            |

  手動修改思考時間或溫度時會切換為「自訂」。

- **進階設定**：每輪模擬場數、GPU 派送葉節點數、執行緒數、模擬策略、選點公式（PUCT／UCT）、探索係數、亂數種子、預先搜尋。
- **介面**：棋譜存取、悔棋、勝率圖表、搜尋紀錄、已證明的勝負與手數，以及預先搜尋時的玩家應手提示。

## 建置與執行

需要 Rust（含 `wasm32-unknown-unknown` target）、[`wasm-bindgen-cli`](https://github.com/wasm-bindgen/wasm-bindgen) 0.2.130 及 Node.js。

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.130
npm ci
npm run build        # 產生 engine.bundle.js（WASM 與 worker 打包在一起）
```

接著用任一靜態伺服器開啟 `index.html`，例如 `python3 -m http.server`。`npm run build:pages` 會把網站檔案複製到 `dist/`。

### 開發指令

```sh
npm run format        # cargo fmt + prettier
npm run format:check
cargo clippy --all-targets -- -D warnings
cargo test            # 單元測試
cargo test -- --ignored                              # GPU 測試（macOS 用 Metal，Windows 用 DX12／Vulkan，Linux 用 Vulkan）
cargo test --release -- --ignored --nocapture <名稱>  # 效能量測與自我對戰
```

推送到 GitHub 後，CI（`.github/workflows/ci.yml`）會檢查格式、跑 clippy 與測試。

## 部署

網站由 Cloudflare Pages 的 Git 整合自行建置與部署：在 Cloudflare 後台以 **Connect to Git** 建立 Pages 專案並連結此 repo，設定如下：

| 設定                   | 值                               |
| ---------------------- | -------------------------------- |
| Production branch      | `main`                           |
| Build command          | `sh scripts/cloudflare-build.sh` |
| Build output directory | `dist`                           |

`scripts/cloudflare-build.sh` 會在建置環境安裝 Rust、`wasm32-unknown-unknown` target 與 `wasm-bindgen` 0.2.130，再執行 `npm run build` 和 `npm run build:pages`。推到 `main` 會更新正式網站，其他分支與 PR 會產生預覽網址。

## 棋規細節

- 黑棋恰好五子即勝，白棋五子以上即勝；黑棋無合法落點時白勝。
- 雙三以「能否延伸為兩端開放、且兩端落子皆恰成五的直四」判定；已成四的線不算三，延伸點不遞迴判禁。
- 每手先判勝，再判滿盤和局。雙方都已無法連成五子時提前判和；只有一方無法連成時繼續。
- 更改棋盤大小或規則會重新開局。

## 搜尋演算法

### 樹與置換表

每次決策由當前局面建樹。節點記錄行棋方、子節點、未展開的候選（每點 1 byte）、模擬數 N 與根方累計得分 W。節點代表局面而不是著手序列：以 Zobrist 雜湊建置換表，不同手順到達同一局面時共用節點，樹因此是有向無環圖。

### 候選著手

1. 先判終局，再看當手方的一步勝點，其次封堵對手的一步勝點。空盤取天元。
2. 其餘保留距任一棋子切比雪夫距離 ≤ 2 的空點，優先能產生兩個勝點（雙重威脅）的著手。
3. 對方能製造雙重威脅時，只保留防守著手：所有反衝四，以及落子後對方不再有雙重威脅點的著手。
4. 其餘依攻守雙方未受阻的五格連線評分排序。為了加速，先統計全盤 572 個五格窗中雙方的子數，每點只需讀經過它的至多 20 個窗。

### 選擇與展開

預設 PUCT：`q + C·P·√(N父 / B) / (1 + N子 / B)`，B 為每輪場數，C = 0.5。先驗 P ∝ (評分 + 1)^1.5；強制集合中各候選的 P 相同。也可改用 UCT：`q + C·√(ln N父 / N子)`，C = 1.414。

廣度由選擇公式決定（first play urgency）：下一個未展開的候選以節點平均得分為 q 參與比較，分數最高時才展開。根節點先展開前 32 個候選。

### GPU 模擬

- 每個葉節點跑一批（預設 64 場）隨機對局，以勝 1、和 0.5、負 0 計分。
- 一次選多個葉節點（自動、1～256），沿路徑加虛擬敗場使選擇分散，再以一次派送模擬。
- 選點與 GPU 計算流水線化：最多兩批同時在 GPU 上，三組緩衝區輪替。
- 自動模式從 16 個葉節點開始，依實測每秒輪數加倍或減半，上限 256。
- 每個葉節點有固定輪號與種子，CPU 能逐場重現 GPU 結果；派送失敗時由 CPU 接手。
- 可選「連五與擋五」模擬策略（有勝點就下、對方有勝點就擋）。實測吞吐降為約 1/5（GPU）、1/3（CPU），棋力沒有穩定提升，預設關閉。

### 證明傳遞（MCTS-Solver）

終局葉節點記為已證明的勝、和或負並向上傳遞：行棋方有一個子節點必勝即必勝；必敗或必和需所有子節點皆已證明，且候選集為完整的強制集合。已證明節點另記到終局的手數（勝方取最短，敗方與和局取最長）。根節點一經證明即停止搜尋；選點時優先最短的必勝、避開必敗。

### 殺法搜尋（VCF、VCT）

- **VCF**：只用連續衝四取勝，逐步加深（最多 12 手四），找到的是手數最少的勝法。三種規則都適用。
- **VCT**：加入活三，以 df-pn 求解，只用於五子以上規則。根節點依序以 5、9、13、17、21 手為上限搜尋。
- 建樹時先在根節點找 VCF（20000 節點），再找 VCT（2000 節點，平均約 10 ms），找到就直接下第一手。
- 樹內每個節點首次展開時以 200 節點上限找 VCF，找到即標為已證明。

一份棋譜第 68 手的必敗局面，證明所需輪數從 17713 輪降到 78 輪。

### 沿用搜尋樹與預先搜尋

AI 落子後保留搜尋樹，玩家思考時繼續在 AI 著手之下搜尋。玩家落子後以置換表找到對應局面，複製可到達的子圖成為新樹，保留模擬數與證明。玩家下了未搜尋過的著手，或棋規、探索係數、每輪場數、模擬策略、種子改變時，從頭建樹。

預先搜尋期間，右側欄可展開「提示」，列出 AI 搜尋到的玩家最佳應手（最多 5 手），並在棋盤上標出排名。

### 多執行緒（根平行化）

輔助 worker 以不同種子對同一局面建立獨立的樹（自動：CPU 模式取核心數且最多 4，GPU 模式為 1），結束後合併根節點統計與證明。

### 難易度與溫度

在根節點已模擬的子節點中依機率 ∝ N^(1/T) 抽樣，略過已證明必敗的著點；T = 0 即最佳著手。已證明的必勝、一步勝、唯一封堵、天元不受溫度影響。

## GPU 實作

- 棋盤以 225 個 u32 依列儲存（0 空、1 黑、2 白）。每個 shader invocation 負責一場；workgroup 大小 32（Intel gen-9 為 8）。Apple GPU 上 32 比 64 快約 2～3%。
- 每場使用私有棋盤與空點清單，隨機挑選後與尾端交換移除。
- 每方維護 15 行、15 列及兩組各 29 條斜線的位元遮罩，落子只更新經過該點的四條線。CPU 查 4 KiB 五連表；GPU 只看落點左右各四格，16 個門檻打包成 8 bytes 常數。
- CPU 與 GPU 共用 xorshift32 亂數（左 13、右 17、左 5；種子 XOR 全域場次編號，零初態改為 1），以拒絕取樣選空點，兩端結果逐場一致。
- 各 workgroup 在共享記憶體加總分數後各寫一個 u32，CPU 一次讀回。
- 試過但沒採用：用占據位元圖挑第 k 個空點（慢 4～14%）；以原子計數器動態領取對局（吞吐降 3～7%）。

Shader 依循 [W3C WGSL 規格](https://www.w3.org/TR/WGSL/)。

## 引擎介面

搜尋輸入包含棋盤、行棋方、種子、時間或輪數預算與局面版本；回傳落點、根節點各著手的得分與訪問數、耗時、後端與版本。越界棋值、黑白數量與輪次不符、已終局及無效預算會被拒絕。介面只接受當局最新版本的結果；重開局或取消時丟棄舊結果。GPU 裝置無法建立或中途遺失時改用 CPU 完成。

## 測試涵蓋

- 四方向、盤緣、長連、最後一手成五、滿盤和局，以及所有回傳落點皆合法。
- 一步勝優先於防守、唯一勝點必擋、空盤取天元。
- 固定種子與輪數下，選擇能深入第二層、對手層採對手觀點、根訪問數等於總場數；同一葉節點逐場比對 CPU 與 GPU 分數，含派送尾端不足一個 workgroup 的情形。
- 思考中重開局，舊搜尋不能落子；GPU 不可用或遺失時仍能完成對局。
